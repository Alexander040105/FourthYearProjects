# JuanMart Data Warehousing Project Charter

**Project:** JuanMart E-Commerce Data Warehouse & Analytics Platform  
**Role:** Lead Data Engineer  
**Scenario:** Metro Manila-based e-commerce platform (artisanal goods, electronics, fashion, groceries)  
**Business Problem:** Finance reports 15% revenue growth; Operations reports a deficit from returns/cancellations. Sales data is scattered across a web form (customers), an old transactional DB (sales), and text-file logs (shipping, third-party). Data is dirty: duplicates, missing fields, inconsistent region naming.

---

## Phase 1: Discovery

### Objectives
- Understand the business question: *Is JuanMart actually profitable when returns and cancellations are accounted for?*
- Inventory all data sources: web form (customer registrations), transactional DB (sales orders), text-file logs (shipping, third-party courier manifests)
- Profile the raw `juanmart_raw_sales.csv` to identify data quality issues

### Data Requirements
- Raw sales extract (`juanmart_raw_sales.csv`) — 12 rows, 6 columns
- Customer registration data from the web form
- Shipping/courier logs (text files)
- Historical sales data from the transactional DB for trend comparison

### Key Findings (from Lab 1.1 Profiling)
- **Duplicates:** 2 duplicate rows (transaction_id 1001, 1005)
- **Nulls:** 2 missing `cust_name`, 2 missing `amount_paid`
- **Inconsistent regions:** 6 raw variants for 2 actual regions (NCR, CALABARZON)
- **Mixed date formats:** `YYYY-MM-DD` and `YYYY/MM/DD` coexist
- **Status mismatch:** `Completed`, `Cancelled`, `Returned` — Finance counts gross; Operations counts net

### Deliverables
- `1.1_data_profiling.ipynb` — profiling notebook
- `juanmart_schema_audit.sql` — diagnostic SQL + 3NF proposal
- `juanmart_health_report.json` — structured data quality report

## Phase 2: Data Preparation

### Objectives
- Build a programmatic cleansing pipeline that transforms raw data into warehouse-ready clean data
- Standardize all categorical values (regions, statuses)
- Handle missing values with business-appropriate imputation strategies
- Quarantine unrecoverable rows instead of silently dropping them

### Data Requirements
- Input: `juanmart_raw_sales.csv` (raw, dirty)
- Output: `cleaned_juanmart_sales.parquet` (clean, typed, deduplicated)
- Output: `quarantined_transactions.csv` (rows that failed validation)

### Cleansing Rules
1. **Deduplication:** Remove exact duplicate `transaction_id` rows (keep first)
2. **Region standardization:** Map all variants to `National Capital Region` or `CALABARZON`
3. **Date standardization:** Convert all dates to ISO `YYYY-MM-DD`
4. **Missing amount imputation:** Fill with median `amount_paid` for that row's standardized region
5. **Quarantine:** Rows missing `cust_name` after cleaning are quarantined with a reason column

### Deliverables
- `juanmart_sanitizer.py` — full cleansing pipeline with discrete functions
- `cleaned_juanmart_sales.parquet` — cleaned dataset
- `quarantined_transactions.csv` — quarantined rows with reasons

## Phase 3: Model Planning

### Objectives
- Design the dimensional model (star schema) for the JuanMart data warehouse
- Identify fact and dimension tables
- Plan SCD Type 2 for `dim_customer` to track historical address/region changes
- Define the grain of the fact table

### Data Requirements
- Cleaned sales data from Phase 2
- Business rules for revenue recognition (Completed = recognized, Cancelled/Returned = not recognized)
- Customer master data for SCD2 tracking

### Dimensional Model Design

**Fact Table:**
- `fact_sales` — grain: one row per transaction
  - `transaction_id` (degenerate dimension)
  - `customer_key` (FK to dim_customer)
  - `date_key` (FK to dim_calendar)
  - `region_key` (FK to dim_region)
  - `status_key` (FK to dim_status)
  - `amount_paid` (measure)

**Dimension Tables:**
- `dim_customer` — SCD2 (customer_key, cust_name, region_key, effective_date, end_date, is_current)
- `dim_calendar` — date_key, full_date, year, quarter, month, month_name, day_of_week, is_weekend
- `dim_region` — region_key, region_name, region_code
- `dim_status` — status_key, status_name, is_revenue_recognized

### Deliverables
- `juanmart_star_schema.py` — Python script to generate star schema diagram (PNG)
- Star schema ERD diagram

## Phase 4: Model Building

### Objectives
- Implement the SCD Type 2 pipeline for `dim_customer`
- Build the ETL logic to load fact and dimension tables from cleaned staging data
- Implement MERGE/UPSERT logic for handling customer region changes over time

### Data Requirements
- Cleaned data from Phase 2
- SCD2 metadata columns: `effective_date`, `end_date`, `is_current`

### SCD2 Logic
When a customer's region changes:
1. Set the existing current record's `is_current = FALSE` and `end_date = new_order_date`
2. Insert a new record with `effective_date = new_order_date`, `end_date = NULL`, `is_current = TRUE`
3. This preserves historical context — sales are mapped to where the customer lived at time of purchase

### Deliverables
- `juanmart_scd_pipeline.sql` — SCD2 MERGE/UPSERT implementation

## Phase 6: Operationalize

### Objectives
- Schedule the cleansing pipeline as a recurring batch job
- Monitor data quality scores over time and alert on degradation
- Enable self-service analytics for Finance and Operations teams

### Deployment Goals
- **ETL Schedule:** Daily batch at 02:00 PHT (after transactional DB backup)
- **Quarantine SLA:** Quarantined rows reviewed and resolved within 48 hours
- **Data Quality Threshold:** Score must stay above 90%; below that triggers an alert
- **Dashboard Refresh:** Streamlit dashboard refreshes on data load completion
- **SCD2 Maintenance:** Customer dimension updates run as part of the daily ETL

### Monitoring & Alerting
- Track `data_quality_score` from `juanmart_health_report.json` over time
- Alert Operations when quarantine count exceeds 5% of daily volume
- Monthly review of SCD2 version counts to detect frequent movers

### Success Criteria
- Finance and Operations reports reconcile to the same net revenue figure
- Data quality score consistently above 90%
- Zero unexplained quarantined rows older than 48 hours
- Dashboard available 24/7 with daily data refresh
